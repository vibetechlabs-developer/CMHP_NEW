B. Backend Connection

Three facts that are easy to get wrong, verified directly against the current code and settings this session:

1. My localhost is not the junior's localhost

If the junior's browser and your Django process are on different machines, http://localhost:8001 in their code will try to reach a server on their own machine, not yours. A reachable, agreed URL is required — there is no way around this.

2. CORS is installed but confirmed DISABLED right now

django-cors-headers is in INSTALLED_APPS and CorsMiddleware is wired in, but a live settings check this session shows CORS_ALLOWED_ORIGINS = [] and CSRF_TRUSTED_ORIGINS = [] — both empty. ALLOWED_HOSTS is still just ['localhost', '127.0.0.1']. Nothing beyond this machine can reach the API yet, by design (safe default), until an origin is added.

3. Cookie/CSRF behavior depends on the setup you choose

The refresh-token cookie is SameSite=Lax, Secure=False (local dev). A same-origin proxy (recommended, see below) avoids every cross-site cookie problem with zero extra setup. A direct cross-origin call from a different host needs CORS_ALLOWED_ORIGINS/CSRF_TRUSTED_ORIGINS set explicitly and still cannot rely on the refresh cookie reaching the server from a browser (SameSite=Lax blocks it on a true cross-site XHR) — only the proxy path gets full session behavior for free.

Once the frontend origin is known — two ways to connect

Recommended: dev-server proxy

In the frontend's dev-server config (Vite server.proxy, CRA "proxy" in package.json, etc.), forward /api to the backend's real URL. The frontend then calls only relative paths (/api/v1/...) — the browser sees everything as same-origin, so no CORS preflight and no cross-site cookie problem exists at all. Set the frontend's API base URL above to /api (or /api/v1 — see the doubled-prefix note below) and leave CORS_ALLOWED_ORIGINS alone.

Fallback: direct cross-origin calls

Only if a proxy genuinely isn't possible. Requires adding the frontend's exact origin to both DJANGO_CORS_ALLOWED_ORIGINS and DJANGO_CSRF_TRUSTED_ORIGINS in backend/.env, plus the backend host/IP to DJANGO_ALLOWED_HOSTS, plus every fetch/axios call sending credentials: "include". Session-restore-on-reload may still not reliably carry the refresh cookie from a real browser under SameSite=Lax across different hosts — budget time to verify this specifically if you must use this path.

Avoiding the doubled /api/v1

Every endpoint in this backend already lives under /api/v1/... (e.g. /api/v1/auth/login/). A common integration bug: the frontend's API_BASE_URL constant is set to http://host:8001/api/v1, and the code also appends /api/v1/auth/login/ to it — producing a request to .../api/v1/api/v1/auth/login/, which 404s. Decide once: either API_BASE_URL stops at the host (no /api/v1), and every call path includes /api/v1/... itself; or API_BASE_URL already ends in /api/v1, and every call path starts directly with the resource (/auth/login/, no repeated prefix). Pick one convention and grep the codebase for the other pattern before shipping.

Explicit reminder

This guide does not change any server configuration, expose any port, or start any server. Filling in the checklist above only fills in placeholders on this page — nothing here talks to the backend. The actual .env edit and server start are separate, deliberate actions you take yourself once the values above are agreed (see §K for the exact next action).

C. Login and Session

The exact backend contract for CSRF, login, current user, refresh, session restoration on reload, and logout — verified directly against apps/authentication/views.py, serializers.py, csrf.py and cookies.py this session, not copied from an older document.

Compact React/TypeScript integration reference

This is a reference pattern only — it has not been integrated into the junior's actual (unseen) frontend, and its exact shape should be adapted to whatever architecture already exists there (state library, existing HTTP wrapper, etc.). It demonstrates the required behaviors: access token in memory only, credentials included for the cookie, CSRF attached on the three POSTs that need it, one coordinated refresh shared by every simultaneously-failing request, at most one retry, and login failures never triggering a refresh attempt.

// api-client.ts — reference pattern, not integrated code
let accessToken: string | null = null;
let csrfToken: string | null = null;
let refreshInFlight: Promise<string> | null = null;

const API_BASE = "/api/v1"; // or your agreed base URL — see §B

async function ensureCsrf(): Promise<string> {
  if (csrfToken) return csrfToken;
  const res = await fetch(`${API_BASE}/auth/csrf/`, { credentials: "include" });
  const data = await res.json();
  csrfToken = data.csrfToken; // exact field name, verified against CsrfBootstrapView
  return csrfToken;
}

async function refreshAccessToken(): Promise<string> {
  // Coordinates concurrent 401s onto ONE refresh call, not one per failed request.
  if (!refreshInFlight) {
    refreshInFlight = (async () => {
      const csrf = await ensureCsrf();
      const res = await fetch(`${API_BASE}/auth/refresh/`, {
        method: "POST",
        credentials: "include",              // sends the HttpOnly refresh cookie
        headers: { "X-CSRFToken": csrf },
      });
      if (!res.ok) {
        clearSession();                        // 401 here = force logout, see §I
        throw new Error("refresh_failed");
      }
      const data = await res.json();
      accessToken = data.access;
      return accessToken!;
    })().finally(() => { refreshInFlight = null; });
  }
  return refreshInFlight;
}

export async function apiFetch(path: string, init: RequestInit = {}, isRetry = false): Promise<Response> {
  if (!accessToken) await refreshAccessToken();  // e.g. right after a page reload
  const res = await fetch(`${API_BASE}${path}`, {
    ...init,
    credentials: "include",
    headers: { ...init.headers, Authorization: `Bearer ${accessToken}` },
  });
  const isLoginCall = path.startsWith("/auth/login/");
  if (res.status === 401 && !isRetry && !isLoginCall) {
    // Never refresh on a failed LOGIN — that 401 means wrong credentials,
    // not an expired session; refreshing would just mask the real error.
    await refreshAccessToken();
    return apiFetch(path, init, true);           // exactly one retry, never a loop
  }
  return res;
}

function clearSession() {
  accessToken = null;
  // also clear workspace context / cached lists here — see §D
}

Session restoration after a browser reload: the access token lives only in memory, so a reload always starts with none. On app start, attempt refreshAccessToken() once (it uses the HttpOnly cookie, which does survive a reload); a 401 there means "no valid session" — send the user to the login screen, this is a normal, expected outcome, not a bug.

D. Workspace Selection

Loading the company/store switcher and the caller's own effective permissions, and the rules that keep one workspace's stale data from leaking into another.

Concepts the junior needs before wiring this up

  • Operating company ≠ the customer placing an order. "Company" here means which of the two operating companies (sharing one physical store) the session is acting as — a completely different concept from the Customer record picked in §E/§F. Never let these share a variable name or a dropdown.
  • Sales orders require company context — every sales-order endpoint is under /companies/<company_id>/.... There is no company-less sales order.
  • Shared-store context is separate from company context entirely — a user can have company access, store access, both, or neither. Phase 1 does not need store access at all (sales orders are company-scoped only) — stores/mine/ is still called for future phases and to show the workspace switcher completely, but the returned list may legitimately be empty for this flow's demo user.
  • Never use a store id as a company id, or vice versa — they are different resources with different permission systems, even though both appear in a "workspace" switcher.
  • Zero accessible workspaces is a legitimate empty state, not an error — render an explicit "you have no company access yet" state, never a blank screen or a spinner that never resolves.
  • UI permission checks are a convenience only. Hiding a button because my-permissions doesn't list a code is good UX, but the backend re-checks permission independently on every request regardless of what the UI showed — never skip error handling for an action just because the UI "shouldn't" have allowed it.
  • Switching workspace must clear scoped state. When the user picks a different company, clear cached customer/product lists, in-progress order forms, and any list-page filters/pagination state tied to the previous company — otherwise a slow network response from the OLD company's list can arrive after the switch and populate the NEW company's screen with the wrong data. The safest pattern: key every cached list/query by company_id (e.g. customers:{companyId}), and cancel or ignore in-flight requests whose company_id no longer matches the current selection when the response arrives.

E. Customer and Product Lookups

Search-select components for the create/edit order form, built against the actual company-scoped list endpoints and their real pagination/filter parameters.

Design notes for 2000+ products

  • Never load the whole catalog into a dropdown. Both list endpoints are paginated (default 20 rows, capped at 100 via ?page_size=) — a naive "fetch everything for the dropdown" approach breaks the moment the catalog grows past a page, and wastes bandwidth well before that.
  • Use ?search= server-side, debounced (300–400ms is a reasonable starting point — not a backend requirement, just a sane default), so the dropdown narrows results as the user types instead of filtering a large client-side list.
  • Filter to active records with ?is_active=true for a picker — showing an inactive customer/product as selectable in a NEW order's picker is misleading (existing order lines that reference an inactive product are a different, already-handled case — see §H).
  • Do not invent a minimum search-length or an unsupported filter — the backend does not require a minimum query length, and the only supported filters are search and is_active for both resources (verified against apps/customers/views.py and apps/products/views.py this session — no category/type filter exists on either).
  • States to render explicitly: loading (a request is in flight), empty (zero results for the current search term — distinct from "no search entered yet"), and error (the request itself failed — see §I). A dropdown that silently shows nothing when the request 403'd is a real support-ticket generator; show the error.
  • Product creation/quick-add is a later task, not required for this phase. Sample customers/products must already exist — demo_sales's company (DEMOA) currently has exactly 1 active customer and 2 active products seeded (verified this session), enough to exercise the picker and create a real order, but not a realistic catalog size. If more sample data is needed for a fuller demo, that is a request to make of the backend side (data seeding), not something the frontend should fabricate.
